## Goal

A conversational front door to the CRM: a volunteer says what they need, the assistant finds the record, makes the allowed change and answers questions from written instructions - instead of people working through screens.

## Run it (Docker, PowerShell)

```powershell
cd C:\projects\crm-assitant
docker compose up -d --build     # build (first time ~5 min) and start
docker compose logs -f app       # watch startup; wait for "Application startup complete"
docker compose exec app python -m pytest -v   # run tests inside the container
docker compose down              # stop
```

Open http://127.0.0.1:8011 (local only; the container listens on 8000 inside).

Database: a `db` service (pgvector/pgvector:0.8.2-pg18, pinned by digest) starts with the app; the app waits for its healthcheck. Data lives in the named volume `crm-assitant_pgdata`, which survives `docker compose down` and container recreation; only `docker compose down -v` or `docker volume rm` deletes it (never do that without the owner). No published port: reachable only from the app container on the compose network. Look at the rows: `docker compose exec db psql -U crm_assistant -d crm_assistant -c "SELECT filename, position, heading FROM chunks"`. Tests use a separate database, `crm_assistant_test`, on the same server.

## User language (29 Oct, docs/instructions19.md; mocked CRM/model + fake-DOM page check only, committed, NOT seen in a real browser)

CHANGED 30 Oct (docs/instructions20.md, owner: "remove toggle"; committed as e12e54e): the chat never changes the language. Removed: the toggle, POST /assistant/language, crm_api.save_language, app/language.py (LanguageState, detection, last-used rule, turn-time save/retry), `language_state` / `language_notice` in turns. Now: the page reads the CRM locale at login and on a resumed login (English when none) and sends `language` with every turn; nothing the user types switches it; the assistant never PUTs /api/preferences. A change made in the CRM shows up at the next login or page reopen (not re-read every turn - choice to confirm). Much of the text below describes the removed rule.

- The language belongs to the CRM user: preference `locale` ("he"/"en") via GET/PUT /api/preferences (sheepsidebay_crm routers/preferences.py, fixes116; PUT refuses other locale values with 400). The CRM value is the only stored copy; the assistant keeps it in the session only.
- Login: after logged_in the server GETs /api/preferences with the new token and adds `language` ("he"/"en"/null) to the login answer; any other key, odd value or failure -> null, login still succeeds. Page: a choice made with the toggle before login wins and is saved after login; else the CRM value; else the browser language (passive, never saved).
- `POST /assistant/language` {"language": "he"|"en"}: rate limit (chat group) -> token (401) -> value (400 `invalid_language`, nothing called) -> CRM login check -> PUT {"key": "locale", "value"}. 200 `saved` / 502 `not_saved` / 401 logout.
- Rule (app/language.py, the shared contract for a future WhatsApp client): `LanguageState` {language, toggled, streak, saved, retry} held by the page, sent with every turn (`language_state`), returned updated. Only typed free text counts: Ask questions and free messages in the contact flow minus the field values the extractor read; never menu choices (empty message), buttons, confirm/cancel/skip words, a leading command verb (planner verbs + please), URLs, emails, digits, punctuation, or ANY apartment-flow message. Clearly = >= 4 letters (Hebrew U+0590-U+05FF, Latin A-Za-z) and one script >= 80%. No toggle this session: one clear message switches; after a toggle: two in a row (a clear message in the current language resets the row; an unclear one doesn't count either way). Toggle press: applies at once, saves, resets. Save only on a change, never the same value as `saved`; a failed save keeps the language, never blocks the turn, and is retried once on the next turn (server side, via `retry`). Nothing but the two letters is stored; no message text or scores logged.
- Design choice: detection and the turn-time save run on the server inside /assistant/turn (same `language.save` as the route), so the rule lives in one place and is tested in Python; the page calls POST /assistant/language only for the toggle.
- Replies: every server text is he/en (GATE_REPLIES, contact/apartment MESSAGES, crm.py demo texts + ADD_CONTACT_POINTER, main CLARIFY/PLACEHOLDER_REPLY, knowledge.TEXTS, language.NOTICES). The answer instruction names the target language ("Write the answer in Hebrew"); retrieval still searches both guides (unchanged).

## Apartment edit (29 Oct, docs/instructions18.md + sheepsidebay_crm fixes115; mocked tests only, committed, NOT run against any CRM)

The old /fields endpoint is gone. The CRM decides the fields per user and apartment; nothing here keeps a field name, label or option list (a test scans the code for them).
- Kinds: single_option / multi_option (numbered lists), yes_no (sent as JSON true/false), text / number (sent as typed; the CRM checks them), date (day first 29/10/2026, 29.10.2026 or 29-10-2026 is sent as 2026-10-29 - owner's choice 29 Oct; an impossible day-first date is asked again; anything else is sent as typed). Clearing only through the "Clear the value" button (owner's choice 29 Oct): it sends `[clear]`; a typed "none" / "ללא" is an ordinary value. A multi list's Save with nothing ticked sends the same `[clear]` (the answer's `clear` entry). Clearing (from the CRM's apartment_edit_rules.parse_value): null clears text/number/date/yes_no, [] clears multi_option, single_option can't be cleared. Report-number option values are integers and are sent as integers. A kind the chat doesn't know is left out of the list.
- State (page, no token): step, ids (apartment_id, lineage_id), chosen field_key, a fingerprint of the list shown, and the pending change (field_key, value, label, old/new text). No field list: every turn after the apartment is chosen re-reads it by lineage, and if the apartment version or the list differs from what was shown, the user sees the new list and is asked again (a number typed for an old list is never applied).

A double yes with the same state is refused by the CRM's version check (409).

## .NET analogies

- An embedding is a list of numbers, like coordinates on a map; similar meanings land near each other.
- Cosine similarity is the angle between two arrows: 1.0 means the same direction.
- pgvector would be a nearest-neighbour index, like SQL Server's spatial index for geography points, but for meaning.
