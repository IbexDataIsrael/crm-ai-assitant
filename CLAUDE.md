## Goal

A conversational front door to the CRM: a volunteer says what they need, the assistant finds the record, makes the allowed change and answers questions from written instructions - instead of people working through screens.

## Run it (Docker, PowerShell)

```powershell
cd C:\projects\crm-assitant
docker compose up -d --build     # build (first time ~5 min) and start
docker compose logs -f app       # watch startup; wait for "Application startup complete"
docker compose exec app python -m pytest -v   # run tests inside the container
docker compose down              # stop
```

Open http://127.0.0.1:8011 (local only; the container listens on 8000 inside).

Database: a `db` service (pgvector/pgvector:0.8.2-pg18, pinned by digest) starts with the app; the app waits for its healthcheck. Data lives in the named volume `crm-assitant_pgdata`, which survives `docker compose down` and container recreation; only `docker compose down -v` or `docker volume rm` deletes it (never do that without the owner). No published port: reachable only from the app container on the compose network. Look at the rows: `docker compose exec db psql -U crm_assistant -d crm_assistant -c "SELECT filename, position, heading FROM chunks"`. Tests use a separate database, `crm_assistant_test`, on the same server.

## Login enforcement (25 Oct, docs/instructions17.md; mocked tests + local server profile only, NOT deployed)

## Apartment edit (25 Oct, sheepsidebay_crm docs/fixes114.md; mocked tests only, committed, NOT run against any CRM)

- Flow (owner's order): menu "Edit an apartment / עריכת דירה" -> the chat asks for the address -> CRM search (address, apartment number or resident; several matches -> numbered list to pick from; "only the first 20" note when the CRM says `truncated`) -> the apartment's full address + id + current values -> the CRM's list of fields this user may edit -> the field's options -> the update -> the reply shows the state the CRM returned after saving (never the value sent). Then another field can be chosen.
- Code: app/apartment_chat.py (stateless; the page holds `apartment_state`, no token in it), app/crm_api.py (apartment_fields, search_apartments, apartment_by_lineage, update_apartment_field), `edit_apartment` intent in app/main.py behind the same login check, page buttons in static/index.html. No AI provider is used in this flow at all (no free-text extraction).
- CRM endpoints (new in sheepsidebay_crm, backend/app/routers/assistant_apartments.py): GET /api/assistant/apartments/fields, /search?q=, /by-lineage/{lineage_id}, POST /{apartment_id}/update {field, value}. JWT only. Fields are not a list kept here: the CRM returns the fields the admin lets this user edit (activist edit locks on the CRM's shliach-config page), each with the org's options. This phase the CRM can write only jewish_status (single) and language (multi).
- Safety: the page disables input and every button while a turn is in flight, and disables older steps' buttons. 409 (changed meanwhile) or 404 -> re-read by lineage id, show the current state, ask for the value again (never resent). Lost answer (timeout, dropped connection, CRM 5xx, unreadable 2xx) -> the edit is BLOCKED: nothing is resent; "yes" re-reads the lineage and says "saved" only if the CRM shows the value that was sent, otherwise "probably not saved, can't be sure" and stays blocked; "no" stops. No connection at all -> "not sent". 401 -> logout; 403 / 422 -> the field list / options are reloaded from the CRM.
- Typed answers: a number from the list, or an option's exact label/value; multi: comma-separated ("1,3"), "none"/"ללא" clears.

## Built (verified 23 October 2026)

- Chat page + FastAPI backend in Docker, port 8011.
- Routing: a bilingual (English/Hebrew) keyword stub (app/planner.py) picks action / knowledge / clarify. It is NOT AI routing. Rule (changed 24 Oct, docs/instructions6.md):
  - action: the message STARTS with a find / add / update command verb (English: find, search, add, create, update; Hebrew imperative and future request forms, e.g. מצא/חפש, הוסף/תוסיף/צור, עדכן/תעדכן), optionally after "please" / "בבקשה", and does not end with "?". Whole words only ("address" is not "add", "updates" is not "update"). A verb inside a question ("how do I add a contact?") is not an action. The planner also returns which demo action (`action`: find/add/update), and crm.pick_placeholder uses it.
  - clarify: empty or whitespace-only input only (the page already refuses to send an empty message; the server has no other input validation).
  - knowledge: everything else, so "what is jewishpoints" and greetings like "hello" search the guides. No list of question words.
  - Known limits: a polite question form without "?" ("can you add a contact") goes to knowledge; a command not starting with a verb ("Dana's phone - update it") goes to knowledge.
- Action route: placeholder CRM functions with demo data (app/crm.py) for find / update. No CRM connection; nothing is changed. A typed add command ("add a contact") now only points to the menu (since 25 Oct, instructions15).
- Chat login + quick menu + add-contact conversation (25 Oct, docs/instructions15_the_whole_picture.md; choices and every CRM-code wording in docs/contact-conversation-design.md). Tested with a mocked CRM and mocked model only; NOT yet run live or seen in a real browser.
  - `POST /auth/login` proxies the page's login form to the CRM's `POST /api/auth/token` (redirects not followed, body never echoed, no-store, no cookie). Multi-organization: `choose_organization` + organizations, then log in again with organization_id. The page keeps the JWT in a JS variable only.
  - `POST /assistant/turn` `{intent, message, state}`: intent only from the menu (create_contact / update_contact = "not available yet", calls nothing / ask_question = unchanged /chat). Server is stateless; the page holds the state (fields, pending proposal, language - no token) and clears it on logout, new login, any 401.
  - app/contact_chat.py runs the loop through the bridge; app/field_extraction.py asks the configured provider (Gemini free tier by default) to read fields from ONE message (no token, no history). No key -> one field at a time. Confirm only on a fixed explicit-yes word list, with the shown proposal's id + hash + fields; edits drop the proposal. Contact details typed in the chat go to the provider - owner's decision before live use on the free tier.
- CRM contact-draft bridge (25 Oct, docs/instructions12.md + docs/instructuions13.md option 1). Structured fields only, NOT conversational AI; /chat and guide Q&A unchanged. Tested with a mocked CRM only - never run against the real CRM.
  - Since instructions17 the chat routes require a CRM-confirmed login (see "Login enforcement"); the bridge routes need the user's token and the CRM checks it. Still no service key of its own (on purpose). Host port bound to 127.0.0.1.
  - `POST /crm/contact-drafts/proposals` body `{"fields": {first_name, last_name, phone, email, address}}` -> CRM `POST /api/assistant/proposals` (action `create_contact_draft`). Answers: 200 `needs_information` (missing_fields, invalid_fields, normalized `fields` to resubmit - no server-side conversation state), 201 `proposal` (proposal_id, payload_hash, expires_at, exact `draft`), 422 `invalid`. Never confirms by itself.
  - `POST /crm/contact-drafts/proposals/{proposal_id}/confirm` body `{"payload_hash": ..., "fields"?: ...}` -> CRM confirm. 201 `created` (contact_id + contact read back by the CRM), 200 `created` with `replayed: true` on a retry. Lost answer (read/write timeout, dropped connection, CRM 5xx, unreadable 2xx) -> 504/502 `uncertain` with the same proposal_id + payload_hash: confirm again, the CRM saves at most once. No connection at all -> 502 `crm_unreachable` (not sent). Also: 409 `payload_mismatch` / `conflict` (retryable), 404 `unknown_proposal` (also for a non-uuid id, which is never sent), 410 `expired`, 401 `unauthorized`, 403 `forbidden`, 502 `crm_redirect_refused` / `crm_contract_error` / `crm_error`.
  - Token: the client sends the user's CRM JWT as `Authorization: Bearer`; forwarded only in that header to CRM_API_URL's origin; redirects never followed; never logged, stored, returned or given to an AI provider. Identity fields in the body (organization_id, user_id) are refused (422). The CRM checks user, organization and permissions.
  - The 409 split relies on the CRM's exact message text "The confirmed details do not match this proposal" (routers/assistant.py); if the CRM changes it, that case shows as a retryable `conflict`.
- Knowledge route: real local semantic retrieval.
  - app/chunking.py splits the listed documents into chunks that keep filename, document title and section heading (changed 25 Oct, docs/instructions7.md). Headings: markdown `#` lines; a document with NO `#` lines (the two guides) uses short numbered lines instead ("1. What this system is": number + dot, at most 8 words, not ending in "."), and its short first line before the first section is the document title. In a document with `#` headings (the fixtures) numbered lines stay ordinary steps. Each chunk is embedded as "title > heading" + text (just the heading when there is no title, or the title is the heading). Headings and titles are context only: a section with no body makes no chunk, so a heading is never a passage by itself. The guide wording is unchanged. Chunk size is measured with the model's own tokenizer, including special tokens, against the model's real limit (128 tokens). Too-long text is split with a small overlap; anything that still can't fit raises an error instead of being silently truncated.
  - app/embeddings.py runs sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2 locally on CPU (pinned revision). Small interface (max_tokens, count_tokens, encode) so another provider could replace it.
  - app/vectorstore.py stores chunks in PostgreSQL + pgvector (since 25 Oct, docs/instructions8.md; before: an in-memory list rebuilt and fully re-embedded at every start). Table `chunks`: collection ("guides" for the app), filename, position, title, heading, text, embed_text, content_hash (sha256 of model + revision + embed_text), embedding `vector(384)`, updated_at; key (collection, filename, position). Startup syncs the table with the guides: same hash at the same position -> kept; same hash elsewhere -> stored vector reused (moved chunk); otherwise embedded; rows whose chunk is gone -> deleted. One transaction, advisory lock per collection, logged as "Vector store 'guides': 54 chunks - N unchanged, N moved, N embedded, N removed". Search is SQL: `ORDER BY embedding <=> question` (cosine distance), score = 1 - distance; exact scan, no approximate (HNSW) index - not needed for 54 rows. A new connection per search, so a recreated database container is picked up. Verified 25 Oct: top-3 rankings and scores for 5 questions identical to the in-memory store; after `docker compose up -d --force-recreate db` the 54 rows and an md5 fingerprint of all vectors were unchanged, and the next app start logged "54 unchanged, 0 embedded".
  - chunking.py / vectorstore.py take a `filenames` list; knowledge.py passes ACTIVE_DOCUMENTS. Current corpus (measured 25 Oct): 54 chunks - 27 from each guide; 51 to 128 tokens each including the title/heading context (limit 128). Before 25 Oct: 47 chunks, 21 to 128 tokens.
  - Sources now show the section: "about_english.md > 1. What this system is" (before 25 Oct: "about_english.md > about_english.md"). The document title is used for embedding, not shown on the page.
  - Both guides contain a placeholder that is now searchable: English "[TO COMPLETE: example questions your team finds useful]", Hebrew "[להשלמה: מי במשרד מאפס סיסמאות ידנית, אם בכלל]".
  - app/knowledge.py returns the top 3 passages with similarity scores, filenames and headings, and builds the reply text.
- Answer generation (app/generation.py). Provider chosen by `ANSWER_PROVIDER` (default `gemini`; `anthropic` for Claude). No automatic fallback between providers.
- Gemini provider (default) - tested live, see below:
  - Gemini through the official google-genai SDK (2.28.0), Interactions API (`client.interactions.create`), which Google's docs recommend for new work. `store=False` so Google doesn't keep the conversation server-side.

## .NET analogies

- An embedding is a list of numbers, like coordinates on a map; similar meanings land near each other.
- Cosine similarity is the angle between two arrows: 1.0 means the same direction.
- pgvector would be a nearest-neighbour index, like SQL Server's spatial index for geography points, but for meaning.
